# Работа с личным GTD

Перед работой выполни `python3 gtd_agent.py GET /capabilities` и `GET /workspaces`.
Источник задач — существующий сервер, доступ из личной переменной `GTD_AGENT_TOKEN`.
Не используй локальную базу или Todoist вместо него. Контракт — `GET /openapi.json`.

Для записи передавать JSON через stdin. Клиент добавляет `request_key`, если его
не задали, и выводит этот несекретный ключ до отправки. Для повторов сохранять
именно его и остальные аргументы. Не генерировать новую операцию после таймаута.

## Поток мыслей

По поручению сохранить мысли выделить отдельные записи, убрать явные повторы,
сохранить сомнения и контекст. Не требовать предварительной структуры сообщения.
Проверить очевидные дубли по актуальным входящим. Выбрать работу или личное по
смыслу; существенную неоднозначность уточнить. Не выдумывать сроков и обязательств.

Отправить `POST /inbox/capture` с `source_text` — исходным текстом сообщения и
`entries` — массивом `{workspace_id,title,description}` (до 50). Сервер атомарно
создаёт обычные активные записи в `inbox`, сохраняет исходник отдельно и возвращает
`capture_id` и созданные карточки. Разделение текста выполняет ассистент; API не
вызывает языковую модель. Голос используется как расшифрованный в чате текст.
Для большего потока использовать несколько явно отдельных пакетов с разными ключами.

## Разбор входящих

Получить `GET /inbox?limit=5`, дочитать все нужные страницы по `next_cursor`.
Полный исходный поток доступен через `GET /captures/{capture_id}`. Найти подходящий
существующий проект через `GET /items?kind=project` до создания нового.

Разбирать небольшими порциями: желаемый результат, нужно ли действие, доступный
следующий шаг, реальные зависимости и даты. Задавать вопросы только там, где ответ
влияет на решение. Сохранить предлагаемые поля и вопросы через
`PUT /inbox/{id}/draft` с `revision`, `draft_revision` (0 для первого), `changes`,
`questions:[{id,question,answer:null}]` и `request_key`. Это не выводит карточку
из входящих. Ответы сохранять тем же способом, обновляя `draft_revision`.

Если `clarification.stale=true`, перечитать карточку и согласовать черновик с
новыми данными. `POST /inbox/{id}/resolve` требует актуальные обе ревизии и
ответы на оставленные вопросы. Он применяет черновик, сохраняет ответы в
комментарии и выводит запись из входящих одной транзакцией. Не придумывать ответы.

Разделы: `projects` — результат нескольких действий; `actions` — разовое дело;
`discuss` — вопрос для обсуждения; `someday` — идея без обязательства.
Проект: `kind=project`, результат в `outcome`; его действия — `kind=action`,
`parent_id` того же пространства. Вложенных проектов нет.

`label=next` — можно делать сейчас, а не обязательно сегодня. `label=waiting`
и `waiting_for` — фактическое ожидание уже переданного запроса. Создание карточки
не отправляет сообщение человеку. Разделение пространства проекта переносит
его дочерние карточки по существующим правилам сервиса; учитывать этот эффект.

## Изменения и даты

Для полного чтения использовать `GET /items/{id}`. Список содержит краткие
превью, поэтому не заменять полное описание его обрезанной версией.
Изменять только нужные поля через PATCH с актуальной `revision` и ключом операции.
При подтверждённом 409 перечитать карточку и заново оценить изменение, затем
создать новую операцию с новым ключом. После неоднозначного сетевого сбоя повторить
исходную операцию с прежними аргументами и ключом.

Сохранять ID и состояние остальных пунктов чек-листа. Завершать и возвращать
карточки через `/complete` (`done:true/false`), не через PATCH. Проект закрывать
после достижения результата и завершения действий. Повторяющийся следующий
экземпляр создаёт сервер — не создавать его второй раз.

Удалять только по поручению через `/trash`, восстанавливать через `/restore`.
Удаление проекта затрагивает его действия. У API нет окончательного удаления.

Понимать относительные даты в Europe/Moscow. `due_date` — дата действия,
`due_time` — время (нужна дата), `deadline` — крайний срок. Не добавлять искусственные
даты для наполнения «Сегодня». Дата в карточке не создаёт уведомление.

## Обзоры

Утром читать `GET /reviews/daily`: сегодня, до конца недели, просроченное,
доступные следующие действия, ожидания, количество входящих и проекты без
продолжения. Отвечать коротким текстом без запуска интерфейса приложения.
Рекомендации отличать от принятых обязательств. Проверять `counts` и `truncated`:
не выдавать обрезанный раздел за полный список, при необходимости дочитать `/items`.

Для недельного обзора использовать `/reviews/weekly` и дочитывать проекты,
идеи, ожидания. Проверить, есть ли у проектов доступное продолжение. Не считать
количество карточек доказательством перегрузки и не менять задачи ради сводки.

Плановая доставка — отдельная функция. Не обещать её после одного вызова API.
Создать расписание только после проверки живого авторизованного чтения в той
же среде исполнения, которая будет выполнять расписание. Предпочтение владельца:
08:00 Europe/Moscow. Существующую Telegram-сводку не менять и не дублировать молча.

## Проверка результата

Подтверждать только результат с `ok:true` и успешный ответ сервера. При необходимости
перечитать затронутую карточку. Не использовать Todoist вместо собственного GTD.
Не отправлять внешние сообщения и не менять другие системы без поручения.
